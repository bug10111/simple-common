# 深度代码自检技能（Code Inspector）

## 触发条件

编码完成后、提交前，用户要求深度代码审查或质量审计时调用本技能。

---

## 工作流程（严格按序执行）

### 第一步：读取变更代码，绘制调用链

1. 用 `read_file` 读取所有变更文件
2. 梳理 Controller → Service → View → Repository 完整调用链
3. 找出同一业务的不同入口路径（如 create 和 update 两条路径），列出对比表

### 第二步：逐维度审查

按下方十二个维度逐一审查，每个维度给出 ✅/❌ 判定。

### 第三步：发现违规立即修复

发现任何 ❌ 违规项，立即修复代码，修复后 `mvn clean compile` 重新编译。

### 第四步：递归自检

修复后**重新进入第一步**，完整重读变更代码，重新执行全部维度审查。**循环直到零违规**。

### 第五步：输出最终报告 + 自检清单

---

## 审查维度（一票否决制）

---

### 一、性能风险

#### 1.1 N+1 查询 / N+1 写入
- **检测点**：循环体内是否存在 DB 查询（`xxxView.xxx()`、`xxxRepository.xxx()`）或远程调用（Feign、RPC），以及循环体内是否存在逐条 `save()` / `updateById()` 等写入操作。
- **判定标准**：只要循环内有 DB/RPC 调用即为违规。循环内逐条 `save()` 同样违规。
- **修复方向**：批量查询（`findAll`）、批量写入（`saves`）。

#### 1.2 树形递归未限制深度
- **判定标准**：递归构建树形结构时，无 `maxDepth` 参数或硬编码上限则违规。

#### 1.3 循环调用外部接口
- **判定标准**：循环内 HTTP/MQ/文件 IO 调用，无缓存或批量合并即为违规。

---

### 二、线程安全

#### 2.1 共享可变状态未同步
- **检测点**：`@Service`/`@Component` 中非 `final` 的成员变量。
- **高危类**：`HashMap`、`ArrayList`、`SimpleDateFormat`、`HashSet`。
- **判定标准**：存在上述非线程安全类作为实例变量且无 `synchronized`/`Lock`/`ConcurrentHashMap` 保护。

#### 2.2 check-then-act 竞态
- **判定标准**：`if (xxx == null) { save(xxx); }` 且无 `@Transactional` + 行级锁保护。

---

### 三、内存风险

#### 3.1 未关闭资源
- **判定标准**：IO 流、DB 连接、网络连接未使用 try-with-resources 或 finally 关闭。

#### 3.2 大对象未限制
- **判定标准**：`findAll` 无条件查询、文件上传无大小限制。

#### 3.3 集合无限增长
- **判定标准**：`static` 集合只增不减、缓存无过期策略。

---

### 四、代码规范

#### 4.1 全限定类名滥用
- **判定标准**：除 import 语句外任何位置使用 `com.xxx.ClassName` 全限定类名即为违规。

#### 4.2 链式调用违规
- **检测点**：业务逻辑中超过 2 个 `.` 的调用链。
- **排除项**：Builder 模式（`@Accessors(chain=true)`）、Stream 终止操作、Optional 判空链。
- **判定标准**：`a.getB().getC()` 这类超过 2 级调用即为违规，必须逐层判空分步承接。

#### 4.3 View 层 neRequest 参数 null 检查
- **检测点**：`findAll`/`findOne` 调用是否传入 `null` 作为第二个参数。
- **判定标准**：`xxxView.findAll(request, null)` 即为违规。
- **原因**：传 `null` 会导致 MyBatis-Plus 条件构造器调用 `null.getId()` 触发 NPE。所有 View 接口均已提供单参数重载。

#### 4.4 枚举值核实
- **检测方法**：`read_file` 读取枚举类源码，逐一比对代码中引用的枚举常量名称。
- **原因**：枚举值推测会导致运行时序列化失败。

---

### 五、SQL 规范

#### 5.1 SQL 注入
- **判定标准**：动态 SQL 拼接、`${}` 代替 `#{}`。

#### 5.2 SELECT *
- **判定标准**：XML 或注解中出现 `SELECT *` 即违规。

#### 5.3 无 LIMIT
- **判定标准**：列表查询无 `LIMIT` 子句即违规（主键/唯一键查单条除外）。

---

### 六、注释规范

#### 6.1 接口 Javadoc
- **判定标准**：Service 接口、Controller 的 public 方法缺少 `@param` 或 `@return`。

#### 6.2 方法内注释
- **规则**：
  - 循环（`for`/`while`）前，必须换行后添加注释说明循环意图。
  - 流式 Stream 操作前，必须换行后添加注释说明操作目的。
  - `if` 条件判断前，必须换行后添加注释说明判断逻辑。
  - 方法内处理不同业务逻辑时，每个独立业务段落前必须换行后添加注释。
  - 注释禁止出现数字序号（"步骤1"、"1."等）。
  - 注释禁止放在行尾。

**正确格式**：
```java
// 查询用户信息
var user = userView.findById(userId);

// 校验用户状态
AssertUtils.isTrue(user.isEnabled(), "用户已禁用");

// 遍历已启用的用户列表
for (var u : users) {
    // 排除当前用户自身
    if (!u.getId().equals(currentUserId)) {
        // 构建通知消息
        notifyList.add(buildNotifyMessage(u));
    }
}
```

**错误格式**：
```java
var user = userView.findById(userId); // 查询用户信息  ← 注释放行尾
// 1. 查询用户  ← 带序号
for (var u : users) { ... }  ← for 前无注释
```

### 七、业务流程与逻辑

#### 7.1 业务逻辑闭环
- **必查项**：
  - 新增前是否校验重名/重复
  - 修改前是否校验数据存在性
  - 删除前是否校验关联数据
  - 状态变更是否校验前置状态
  - **覆盖更新场景**：一对多关系更新时，子表是否先删后增。禁止直接追加插入导致数据翻倍。

#### 7.2 异常处理
- **判定标准**：catch 块空实现或只打日志不抛出即为违规。
- **要求**：使用 `AssertUtils` 做参数校验。

---

### 八、数据流转

#### 8.1 数据完整性
- **必查项**：
  - `createUserId`、`createTime` 是否从上下文获取，而非请求参数
  - `updateUserId`、`updateTime` 是否正确后台赋值
  - 枚举值是否在合法范围内

#### 8.2 关键字段生命周期追踪
- **检测方法**：追踪关键业务字段（如 `countField`、`status`）在整个生命周期中的来源和流转。
- **必查项**：
  - 创建时字段从何处获取
  - 修改时字段是否保留了数据库权威值
  - 不同路径（如 create-auto vs create-config 单独创建）赋值逻辑是否一致
  - 是否存在字段为 null 的链路缺口

#### 8.3 请求参数合理性
- **规则**：用户ID、租户ID、创建时间 → 必须后台获取，不可信任前端传入。

---

### 九、代码一致性

> 核心原则：同样业务逻辑在不同路径中必须保持一致的实现方式。

#### 9.1 同类业务路径对比
- **检测方法**：列出同一业务的不同入口路径（如 create vs update、手动打标 vs 自动打标），逐项对比。
- **对比维度**：
  - 数据来源是否一致（如 countField 从数据库取还是从请求取）
  - 校验逻辑是否一致
  - 级联操作是否一致
  - 兜底策略是否一致

#### 9.2 对比表示例
```
| 维度 | 路径A（create） | 路径B（update） | 是否一致 |
|------|----------------|----------------|---------|
| countField来源 | request | tagGroup.get() | ❌ 不一致 |
| 旧数据清理 | 无需 | deleteOld | ✅ 合理差异 |
```

---

### 十、无效操作

> 核心原则：代码中不应存在无意义的查询、重复校验、永远用不到的结果。

#### 10.1 查询结果未被使用
- **检测方法**：检查 DB 查询结果是否在后续逻辑中被实际使用。
- **典型场景**：查询了配置项构建 Map，但走了 else 分支根本没用到这个 Map。

#### 10.2 重复校验
- **检测方法**：同一字段是否在 Controller（`@Validated`）和 Service 层被重复校验。
- **注意**：区分合理重复（Controller 做格式校验，Service 做业务校验）和无意义重复。

#### 10.3 条件分支中的冗余操作
- **检测方法**：在 if/else 之前执行的查询/计算，是否在所有分支中都被用到。

---

### 十一、孤儿数据

> 核心原则：级联删除必须覆盖所有关联的子表数据。

#### 11.1 级联删除完整性
- **检测方法**：修改/删除操作是否清理了所有关联的子表数据。
- **典型场景**：
  - 删除标签组时，是否同时删除了配置项、控件、标签、映射关系
  - 更新时，"删旧建新"策略是否覆盖了所有历史模型（如旧模型手动标签 + 新模型配置项）

#### 11.2 跨模型数据清理
- **检测方法**：当业务存在新旧两套模型时，清理逻辑是否覆盖了旧模型数据。
- **典型场景**：自动打标更新时，是否清理了旧的"手动打标"标签。

---

### 十二、接口排序

#### 12.1 排序字段规范
- **规则**：`sort` 非必填时，系统自动获取该组最大排序值 +1。

#### 12.2 排序默认值逻辑
```java
if (request.getSort() == null) {
    // 获取同组最大排序值
    Integer maxSort = xxxView.findMaxSort(request.getGroupId());
    request.setSort(maxSort == null ? 1 : maxSort + 1);
}
```

## 铁律

1. **全量审查**：所有变更代码必须过一遍，不允许抽查。
2. **逐文件逐方法**：每个修改过的文件、每个修改过的方法都要检查。
3. **以实际代码为准**：通过 `read_file` 验证，不推测，不确定时中断询问用户。
4. **违规必报**：任何违规项必须写入报告，标注文件路径和行号。
5. **给出修复方向**：每条违规项必须附带修复建议。
6. **分级输出**：严重（🔴）、中等（🟡）、轻微（🟢）。
7. **递归自检**：发现违规修复后，必须重新全量审查，直到零违规。
8. **强制编译**：每次修复后必须 `mvn clean compile` 通过。
